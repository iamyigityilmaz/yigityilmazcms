Webhooks don't always arrive: reading Instagram comments by polling

In the demo setup of my Instagram bot, DMs arrived over the webhook without trouble. Comments sometimes came late and sometimes not at all. The fix was to ask for them myself at regular intervals.

How a webhook differs from polling

With a webhook the other side tells you: when something new happens, it sends a request to your address. With polling you do the asking: at regular intervals you check whether anything is new. A webhook is fast and cheap, but whether the notification arrives is out of your hands.

The setup I ended up with

  • DMs still arrive over the webhook.
  • For comments, a scheduler runs every minute and reads the newest 25 comments on the last three posts.
  • If a comment is missed, a catch-up round tries again a few minutes later.

Never answering the same comment twice

The price of polling is repetition: you see the same comment again every minute. So right before sending a reply, the flow asks Instagram whether that comment has already been answered. If it has, the flow leaves it alone.

Asking the source instead of trusting my own list keeps working when the flow restarts or the list is reset.

Being able to see what happened

At the end of every round I keep a short summary record: how many comments were read, how many were new, how many were answered, and how many were skipped and why. When a comment goes unanswered, that record is the first place I look.

A tunnel for local development

n8n runs on my own computer. For Meta to send webhooks it needs an address reachable from outside, which I get from cloudflared's quick tunnel:

cloudflared tunnel --url http://127.0.0.1:XXXX

Replace XXXX with your own port number. The one catch is that the address changes on every start. When the tunnel restarts, the Callback URL in the Meta panel has to be updated. So that I don't forget, I wrote a small PowerShell script that starts n8n and the tunnel and copies the new address to the clipboard.

Which one, and when

If notifications arrive reliably, a webhook is enough. If they don't, or if a missed event is costly, adding polling next to the webhook makes the system safe. In my case an unanswered question costs far more than one extra request per minute.
